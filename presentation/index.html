Composite-Key Memory — Architecture Differentiation
Without composite keys

The application ends up owning job identity.

In Memory, one identifier(address) maps to one profile. A field technician with one phone number and multiple jobs would have one profile in Memory. The application will need to keep track of the multiple jobs for each technician and the conversations for each job. The router has to consult a database to figure out which job the tech is currently on — and which conversation is currently active for that job. Twilio Memory becomes redudant as it only holds the technician details, which would best be saved in the application's DB too.

Runtime flow · single-profile fallback

Two systems hold state. Twilio holds the SMS wire; the app holds every semantic fact about the job.

Without composite keys

Memory becomes redundant!!!

A load-bearing application handler and database
You need at minimum three tables — jobs, active_job_for_phone, and job_conversation_map. Truth splits between Twilio and DB, and they must stay in sync through every failure mode: dropped webhooks, retries, partial writes.
Risk of losing Twilio Memory
Writing per-job observations or summaries pools them into a single bucket that Recall can't disentangle. Teams will end up either not using Memory for job data at all
Conversation Intelligence will bypass Memory
CINTEL summaries arrive keyed by conversationId and profileId. To attribute one to a job, the callback handler must first look up job_id and then save in application DB
Job history is a join, not a fetch
"Show everything from job 4520" means: query the application DB for all conversation IDs, fetch each conversation's transcripts and summaries from Twilio
Multi-system deletion & audit
Deleting one job's memory requires selectively removing rows across your DB and filtering Twilio observations by tag.
With composite keys

Twilio owns the complete (phone, jobID) identity.

One phone number resolve to many distinct Memory profiles — one per job. The router is a single Twilio lookup; Everything about the job is in the profile trait. No application database necessary.

Runtime flow · composite (phone, jobID) key

One system. Job identity, memory, and conversation lineage all live on the same profile — Twilio holds them together.

With composite keys

Conversations implicitly works

Job isolation as a Twilio primitive
The matching rule phone AND jobID resolves the right profile at write time. No external DB required for routing.
Naturally scoped memory
Every observation and summary attaches to the job's own profile. Recall needs to only return one profile's history .
Conversation job states per technician
One active job, others inactive, historical ones completed — all coexist for the same phone. The router picks the active job by a single trait check: Job.conversation_ID and Job.status = active.
Job history survives conversation churn
Reactivating a job creates a fresh conversation on the same profile. Prior ConversationSummaries are already attached to the technician's profile (phone, jobID)
CINTEL summaries land on the right profile automatically
Post-conversation operator results carry the customer participant's profileId. Summaries and observations post to the correct (phone, jobID) profile with no attribution logic in the callback handler.
Clean deletion & compliance boundary
Each job's memory is a discrete, deletable unit.

Differentiation

Composite-key brings identity into Twilio.

State of truth lives in Twilio Memory.

Without composite keys

GA Memory · one profile per phone
  • State of truth: your DB — jobs, active_job_for_phone, job_conversation_map.
  • Router: DB call + Twilio call, per message.
  • Twilio Memory: at risk of going unused — per-job writes pool into one profile.
  • Job scoping: app-owned tags & filters, if teams bother writing to Memory at all.
  • Job history: a multi-system join.
  • CINTEL summary: bypasses Memory — handler looks up job_id, saves to app DB.
  • Deletion: row-by-row across two systems.

With composite keys

Gated Memory · one profile per (phone, jobID)
  • State of truth: the profile trait.
  • Router: one Twilio lookup.
  • Twilio Memory: is the source of truth for the job.
  • Job scoping: the profile boundary itself.
  • Job history: one unscoped Recall.
  • CINTEL summary: lands on the right profile automatically.
  • Deletion: drop the profile.

The gated feature isn't a convenience — it's the difference between Memory going unused and Memory doing the work for you. For a multi-job-per-phone workflow, that's the whole architecture.
