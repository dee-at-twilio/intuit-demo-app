Composite-Key Memory · Architecture Differentiation
Intuit · Field Dispatcher · Gated Feature Comparison
Slide 1 · With Composite Keys

One profile per (phone, jobID). Job isolation is a Twilio primitive.

The gated composite-key feature lets a single technician's phone number resolve to many distinct Memory profiles — one per active or historical job. Twilio holds the identity, the state, and the memory. The application is thin.
Runtime flow · composite key

Job isolation without an app-side database

Twilio's composite matching rule phone AND jobID resolves the right profile at write time. The app never maintains a phone → active_job lookup table.

Naturally scoped memory

Every observation and summary lives on the job's own profile. Recall returns only that job's history — no cross-job leakage, no client-side filtering.

Concurrent state per technician

One active job, others paused, historical ones completed. Router picks the active one by a single trait check: Job.status = active.

Job history survives conversation churn

Reactivating a job creates a fresh conversation on the same profile. Prior ConversationSummaries are already attached — the LLM sees them via unscoped Recall.

CINTEL summaries land automatically

Post-conversation operator results carry the customer participant's profileId. Summaries and observations are posted to the correct (phone, jobID) profile with no per-job routing logic.

Compliance & auditability

Each job's memory is a discrete, deletable unit. Delete a profile — its observations, summaries, and conversation linkage vanish together. One job, one boundary.

Net effect: the router is one Twilio call. The state of truth is the profile trait. There is no app-side database.
Slide 2 · Without Composite Keys · GA Memory

One profile per phone. The application has to rebuild job isolation on top.

GA Memory allows only one profile per identifier value. A technician with three concurrent jobs has one profile, and that profile's observations and summaries pool together. Job scoping must be reconstructed in application code and an external database.
Runtime flow · single-profile fallback

An external database becomes load-bearing

You need jobs, active_job_for_phone, and conversation → job tables. The state of truth splits between Twilio and your DB — and they must stay in sync.

Memory pools across jobs

All observations and summaries attach to one profile. To keep jobs separate you must tag every write with a jobID in source or content, then filter every Recall result client-side.

Context leakage risk

If a filter is missed or a summary is written without a tag, the LLM answering about job 4522 sees observations from job 4521. That is a hard bug to detect and a real risk in a field-service context.

CINTEL summaries need routing logic

The operator result lands on the phone-level profile. To attribute it to a job, the callback handler must look up conversation_id → job_id from your DB and rewrite the summary source or store the mapping elsewhere.

Job history requires a join

“Show me everything from job 4520” is a filtered Recall plus a DB query, not a single profile fetch. Reactivating a job means replaying that join into the LLM prompt.

Higher operational surface

Two systems to back up, two systems to reconcile after a partial failure, two schemas to migrate. Every new job-scoped behavior costs application code and tests.

Net effect: Twilio holds identity for the technician; the application holds identity for the job. Job isolation is now the app's problem — including its correctness, its audit trail, and its failure modes.
